# 持仓分析・管理ツール

長期保有している金融資産を、ローカルで全部計算して Markdown レポートにし、
その判断を Claude Code にさせるためのツール。

## 設計の要点

**計算はローカル、判断は Claude Code。** この分離が中心にある。

```
config/holdings.yaml          自分の持仓（手入力）
        ↓
src/marketdata.py             yfinance + SQLite キャッシュ + 異常バー検出
        ↓
src/analytics.py              評価・損益・配分・集中度・リスク・リバランス
        ↓
reports/latest.md             Markdown レポート
        ↓
Claude Code で「これを読んで分析して」    ← 判断層
```

この構成にしている理由は課金の分離にある。

| | 誰に払うか |
|---|---|
| このツールの計算 | **無料**（ローカルの Python だけ。LLM を一切呼ばない） |
| Claude Code での判断 | **Claude Pro / Max のサブスクに含まれる** |
| Anthropic API | **使わない**（使うなら Console で別途クレジット購入が必要） |

スクリプトから `messages.create()` を呼ばない限り、API クレジットは不要。
Claude Pro のまま運用できる。

> ⚠ 環境変数に `ANTHROPIC_API_KEY` が設定されていると、Claude Code は
> サブスクではなくその API キーで課金する。Pro で使いたいなら設定しないこと。
> `/status` で今どちらを使っているか確認できる。

## セットアップ

```bash
pip install -r requirements.txt
```

```bash
cp config/holdings.example.yaml config/holdings.yaml
```

`config/holdings.yaml` を自分の持仓に書き換える。金額が入るので `.gitignore` 済み。

## 使い方

台帳の検証だけ（価格取得なし・即座に終わる）:

```bash
python -m src.cli validate
```

価格と為替が取れているか確認:

```bash
python -m src.cli quotes
```

レポート生成:

```bash
python -m src.cli report
```

`reports/latest.md` が出力される。これを Claude Code に読ませる:

```
reports/latest.md を読んで分析して
```

|---|---|

### Claude Code から操作する（PC が無くてもよい）

Claude Code（ブラウザ・タブレット・スマホのクラウドセッションでも可）で、
次のスラッシュコマンドが使える。持仓は会話で伝えれば台帳に反映される。

| コマンド | 内容 |
|---|---|
| `/review` | 台帳を検証してレポートを作り、判断まで返す |
| `/add-trade` | 「トヨタを 100 株 2800 円で買った」のような文から取引を記録し、台帳に反映する |
| `/plan` | 積立の割り振りと NISA 枠の消化を説明する |
| `/compliance` | 独立性の確認状況を整理し、報告された結果だけを記録する |

クラウドセッションでは、環境が回収されると `config/holdings.yaml` などの個人データは消える。
専用の非公開リポジトリに置くか、更新のたびに手元に控えること。
また、株価の取得先（Yahoo Finance）がネットワーク制限で届かない場合は、
環境設定の Network access で `query1.finance.yahoo.com` などを許可する。

### 金額を自分で入力するページ（`web/ledger.html`）

証券会社アプリの評価額をそのまま円で入力する、ブラウザだけで動く台帳ページ。
タブレットやスマホで使える。**入力した金額はブラウザ内（localStorage）にだけ保存され、
送信されない。** 配分・目標との差・1 銘柄の上限・現金の下限・集中度を計算し、
**金額を含まない比率だけの要約**を作る。その要約をコピーして Claude Code に貼れば、
金額を渡さずに判断を相談できる。

- 株価や為替は取得しない（評価額を手入力する）。Python 版の相関・リスク指標は出ない
- ブラウザのデータを消すと入力も消える。ページ下部の「バックアップ」をメモに控えておく
- Claude Code の Artifact として公開して使う。単体の HTML ではなく、公開時に枠が付く断片

### 著名投資家の動向（同じページの「著名投資家の動向」タブ）

SEC の 13F（四半期ごとの保有報告）から、バフェットなど約 40 人・社について
**投資家ごとの注目分野（業種の比率と前期比）・上位 10 銘柄・新規購入・全売却**と、
集中投資型の投資家全体で「買われた／売られた／共通して持たれている」銘柄を表示する。

**リアルタイムではない。** 四半期末の保有を 45 日以内に出す制度なので、常に 1〜4 か月前の姿。
提出期限（2 月・5 月・8 月・11 月の 14 日ごろ）の後に、次の手順でデータを作り直す。

```bash
export SEC_USER_AGENT="JevInvest research you@example.com"   # SEC は連絡先を必須にしている
python tools/fetch_13f.py            # 直近 2 四半期を取得（前期比のため）
python tools/export_13f_json.py      # → web/investors.json
```

- 業種は各社が SEC に届け出た SIC コードから大まかに分類（`tools/sectors.py`）。証券会社の業種分類とは一致しないことがある
- 売買は株数の前期比で判定（±10% 以上）。オプション（プット・コール）の行は保有から除外
- 運用会社は改組で CIK が変わる（Greenlight → DME Capital、Pershing Square → Pershing Square Inc. など）。
  最新四半期の報告が無い投資家は集計から外し、ページに明示する

## ガードレール

`config/holdings.yaml` の `guards:` に基準を書くと、レポートで実際に突き合わせて
違反を出す。設定値を置いてあるだけでは意味がないので必ず検査する。

```yaml
guards:
  max_single_position_pct: 20.0        # 個別銘柄 1 つの上限
  min_cash_pct: 5.0                    # 現金比率の下限
  high_correlation_threshold: 0.8      # これ以上の相関ペアを警告する
```

| 基準 | 検査内容 |
|---|---|
| `max_single_position_pct` | 銘柄ごとのウェイト。上限超えは違反、上限の 9 割超は注意。`single_position_exempt_classes` に挙げた資産クラス（コアのインデックスファンド・債券など）は対象外 |
| `min_cash_pct` | 現金比率が下限を下回っていないか |
| `high_correlation_threshold` | 基準通貨建て日次リターンの相関。両方が 2% 以上のウェイトを持つペアのみ対象 |

**同一銘柄を複数口座で持つ場合は合算して判定する。** これをやらないと
「特定口座 14.8% + NISA 14.8%」が両方とも上限内と判定され、合計 29.6% の
集中を見逃す。実際にその構成でテストして検出を確認してある。

相関の対象を「両方 2% 以上」に限っているのは、微小な保有どうしの相関を
並べても判断材料にならないため。

## レポートに入るもの

- 評価額・取得原価・損益（基準通貨建て）
- **損益の「値上がり益」と「為替差益」への分解** — `cost_fx_rate` を書いた銘柄のみ。
  円建て投資家が米国株を持つ場合、これを分けないと何で儲かったのか分からない
- 資産クラス別 / 口座別 / 通貨別の集計
- 集中度（HHI、実質銘柄数 = 1/HHI、上位N銘柄比率）
- リスク（年率ボラ、最大DD、分散効果、ベータ、相関行列）
- 目標配分との乖離とリバランス調整額
- **Claude が判断すべき論点のリスト**

## 実装上の注意点（間違えやすい箇所）

### 評価額とリターン計算で価格を使い分けている

- **評価額** → 実際の価格（`close`）
- **リターン・ボラ・相関** → 配当再投資後（`adj_close`）

BND のような債券 ETF は配当が収益の大半なので、調整前で計算すると
「債券はほぼ無リターン」という誤った結論になる。

### 異常バーを検出して除外している

無料データソースには「数日だけ 10 倍ずれた値」が実際に混ざる。
開発中に `1306.T` で遭遇した例:

```
2026-03-27   382.70
2026-03-30    37.64   ← 配信ミス
2026-03-31    37.14   ← 配信ミス
2026-04-01   389.20
```

放置すると -90% → +948% の日次リターンになり、年率ボラが **541%** と出る
（実際は 20% 程度）。`marketdata.py` が以下で判定している:

- 1 日で ±50% を超える動きを候補にする
- 数営業日以内に元の水準へ戻る → データ異常として除外し、警告を出す
- 戻らない → 実際のイベント（未調整の分割、本物の暴落）なので**勝手に直さず警告のみ**

除外した場合はレポート冒頭に必ず出る。黙って直したりはしない。

### リスク指標は「実際の運用成績」ではない

「今のウェイトをこの期間ずっと保有していたら」という仮定計算。
実際には売買していたはずなので、過去の自分のリターンとは一致しない。
取引履歴から実績を出すには別の実装が必要。

### 価格が取れなかったものを 0 にしない

評価不能として集計から外し、件数を警告に出す。
黙って 0 円扱いにすると全部の比率が狂う。

### 投資信託は手入力

一般の投資信託は API で基準価額が取れない。
`price_override` に[投信協会の投信総合検索ライブラリー](https://toushin-lib.fwg.ne.jp/)の
CSV から転記する。`FUND-` で始まる symbol は価格取得をスキップする。

## 著名投資家の 13F 集計

SEC EDGAR から 13F-HR（機関投資家の四半期保有報告）を直接取得して集計する。
アグリゲーターサイトを経由しないので、**数字の出所が SEC への提出書類そのもの**になる。

```bash
python tools/fetch_13f.py              # config/investors.yaml の全件を取得
python tools/fetch_13f.py --limit 5    # 先頭 5 件で試す
python tools/analyze_13f.py            # 集計して reports/investors-13f.md を出力
```

> ⚠ 環境変数 `SEC_USER_AGENT` に連絡先を含む文字列を設定すること（例: `export SEC_USER_AGENT="JevInvest research you@example.com"`）。
> SEC は fair access policy で連絡先の明記を要求している。

対象は `config/investors.yaml` で編集できる（同梱は約 40 名の例。自分の名簿に育てる）。
`cik` を明記すると名前解決をスキップする。名前で見つからない運用者は、
`fetch_13f.py` が最後に「未解決」として一覧する。

### 購入候補の抽出とティッカー解決

```bash
python tools/screen_candidates.py --top 25
python tools/screen_candidates.py --styles value quality   # スタイルで絞る
```

`reports/candidates.md` に、**ティッカー付きの候補リスト**と
`config/compliance.yaml` への追記用 YAML が出る。

13F には発行体名しか入っていないので、**CUSIP から OpenFIGI（Bloomberg の無償
マッピング）でティッカーを解決**している。発行体名での照合は捨てた — 実データで
3 種類の失敗が出たため:

| 失敗 | 実例 |
|---|---|
| 総称名の衝突 | `ISHARES TR` は数百の iShares ETF が共有する名前。名前照合は一致度 1.00 で **SLV（銀 ETF）を返したが、CUSIP 別では IVV（S&P500）と IWM（Russell2000）だった** |
| 略語 | `APPLIED MATLS INC` の `MATLS` は `MATERIALS` の略で前方一致しない |
| 切り詰め | 28〜30 文字で切られている提出が多い（`TAIWAN SEMICONDUCTOR MANUFAC`） |

CUSIP は一意なのでこれらが全部消える。結果は SQLite にキャッシュする。

### 集計で処理している落とし穴

実際にデータを取って見つかった問題。どれも黙って間違った数字を出すもの。

| 問題 | 症状 | 対処 |
|---|---|---|
| **同一運用会社の複数 CIK** | D.E. Shaw は CIK が 3 つあり 2 つは 2005 年で提出停止。Baupost も旧法人が 2002 年で停止 | 候補の中から**最新の報告日を持つ CIK** を選ぶ。「13F がある最初の候補」を採ると 20 年前のデータを静かに返す |
| **value の単位が提出者ごとに違う** | 2023 年の規則改正で千ドル→ドルになったが、2026 年でも千ドルで出す会社がある（Baupost）。誤ると保有額が 1000 倍ずれる | 行ごとの 1 株単価の**中央値**が $1 未満なら千ドル単位と判定 |
| **同一銘柄が複数行に分かれる** | マネージャー別・議決権別に別行で出るため、そのまま集計すると保有額が過小 | CUSIP とクラスでまとめる |
| **議決権クラスの二重計上** | GOOG と GOOGL は CUSIP が別。同じ会社が両方持つと保有者数が 2 票になる | まず (運用会社, 発行体) でまとめてから発行体単位に集計 |
| **提出が止まった運用会社** | 解散・買収された会社が古い報告日で残る（Alleghany は 2022 年、Research Affiliates は 2013 年） | 最新四半期以外を**除外**し、除外した会社をレポートに明記 |
| **クオンツが票を独占** | 数千銘柄持つ運用会社が全銘柄に票を入れ、breadth 集計が大型株一覧になる | 50 銘柄以下の「選別型」に絞った集計を別に出す |
| **NaN は Python では真値** | `if not name` で NaN を弾けず `str(nan)` = `"NAN"` になり、**未解決の CUSIP 78 件が「NAN」という 1 社にまとまって「保有者 41 社」という実在しない銘柄が首位に出た** | `pd.isna()` で明示的に判定。`fillna(Series)` に頼らず内包表記で組む |
| **shareClassFIGI は会社 ID ではない** | 株式クラスの識別子なので GOOGL と GOOG で別値になり、議決権クラスがまとまらない | FIGI の標準化された名称からクラス表記（`-CL A` 等）を落としてまとめる |

### 13F の限界（レポート冒頭にも明記してある）

- **米国上場の株式ロングのみ。**現金・債券・非米国株・空売り・非上場事業は写らない。
  Berkshire の巨額の短期債も写らないので、13F を「その人の資産配分」と読むのは誤り
- 四半期末から 45 日後の提出なので常に 1〜4 ヶ月古い
- 取得単価と保有期間が写らない。数十年保有で含み益が巨大な銘柄は税金の都合で
  売れないだけの場合がある
- 米国外の運用者は米国保有分だけが見える（Fundsmith、Lindsell Train など）
- **生存者バイアス。**名簿は「今有名な人」で作られており、同じ手法で失敗した
  運用会社は入っていない

## データソースについて

`yfinance` は Yahoo Finance の非公式ラッパー。

- 15 分程度の遅延がある（長期保有の分析では無害）
- レート制限のしきい値が非公開で、IP 単位で数時間〜数日ブロックされることがある
- 429 のとき例外を投げずに**空の DataFrame を返す**ので、失敗が静かに起きる
- **個人の分析用途に限定すること。** 商用利用・データ再配布は規約上避けるべき

対策として SQLite キャッシュを必ず通し、銘柄ごとのループではなく一括取得している。

日本株でより信頼できるデータが必要なら:

| 手段 | 特性 |
|---|---|
| [J-Quants API](https://jpx-jquants.com/) | JPX 公式。**無料プランは 12 週間遅延・過去 2 年**なので時価評価には使えない |
| 立花証券 e 支店 API | 口座開設無料でリアルタイム株価・板情報・20 年分の日足 |

## 法務・コンプライアンス

- **個人の自己利用に留めること。** 他人に判断を提供・販売すると
  金融商品取引法上の投資助言・代理業に触れる可能性がある
- 実発注機能は持たない。分析と判断支援のみ
- 業務環境・業務端末とは切り離して扱うこと
